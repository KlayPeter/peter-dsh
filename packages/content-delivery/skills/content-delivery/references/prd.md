# PRD

回答：谁遇到什么问题，产品需要表现出什么行为，怎样判断完成。

按实际规模组织：问题与用户 → 目标和范围 → 场景与流程 → 需求及验收 → 约束依赖 → 待确认项。已知上下文足够时直接写，不机械重复访谈。

把核心需求写成可观察的行为，并配对应验收条件。成功指标的基线、目标和统计口径来自用户或资料；未知就标为待确认。功能有失败、空状态、权限或边界条件时写清楚。

需求和实现方案分开。PRD 可以说明已知技术约束，不替研发凭空决定数据库或框架。AI 输出质量要求应说明如何评估，不用一次演示证明稳定性。

图示选择：分支用户流程、状态变化、必要的页面线框；简单需求清单用表格。

读者检查：产品能否确认范围？研发能否理解行为？测试能否据此写用例？

需要完整范例时，按需读 upstream.md 中的 GitHub prd 或 deliver-prd；两者选一为主，避免重复加载。
